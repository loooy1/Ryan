# RCS 车辆协议适配器与虚拟车协议

更新日期：2026-10-05。

## 调用链与文件

`task_receive → 任务服务 → 调度器分配车辆 → 执行服务调用算法 → 统一车辆命令通道 → 按车辆 Protocol 选择适配器 → 车辆`

| 位置 | 职责 |
| --- | --- |
| Shared/Contracts/Rcs/Protocol/VehicleProtocol.cs | 路径点、动作、命令、接收确认和完成结果。 |
| RCS/Backend/Modules/Rcs/Protocol/IVehicleCommandChannel.cs | 执行服务依赖的发送和等待完成接口。 |
| RCS/Backend/Modules/Rcs/Protocol/VehicleCommandChannel.cs | 按车辆编号路由到协议会话，记录统一命令及执行结果。 |
| RCS/Backend/Modules/Rcs/Protocol/IVehicleProtocolAdapter.cs | 车型协议适配器和标准化车辆会话接口。 |
| RCS/Backend/Modules/Rcs/Protocol/VirtualVehicleProtocolAdapter.cs | 当前唯一内置适配器，将统一命令接到进程内虚拟车。 |
| RCS/Algorithms/IPathPlanningAlgorithm.cs | 接收地图、车队位置/目标点上下文和规划设置，输出不带业务动作的路线。 |
| RCS/Algorithms/Traffic/MultiVehicleTrafficCoordinator.cs | 接收 RCS 推送的位置与目标点，管理路径点/线预约、释放和规划上下文。 |
| RCS/Backend/Modules/Rcs/Application/Execution/RcsTaskRoutePlanner.cs | RCS 将目标站点交给算法，输出只含移动点的路线。 |
| RCS/Backend/Modules/Rcs/Application/Execution/RcsTaskExecutionService.cs | 推送车辆状态、发送路径段；续发冲突时尝试暂停并自动改路。 |
| RCS/VirtualVehicle/VirtualVehicleSimulator.cs | 接收命令、逐点移动、执行动作、报告状态及完成结果。 |

车辆表已有 `protocol` 字段，车辆管理的新增和配置页面可选择后端注册的协议类型。`GET /api/rcs/vehicles/protocols` 返回可用协议。RCS 执行层只使用 `IVehicleCommandChannel`；命令通道按车辆配置把命令路由到 `IVehicleProtocolSession`，会话由匹配的 `IVehicleProtocolAdapter` 创建。当前只注册 `VIRTUAL`，尚未包含真实厂商协议；增加车型时实现并注册适配器即可，不修改调度、路径算法和任务层。未知/未注册协议的历史车辆会显示为不可用且不会被调度，不会阻止其余车辆启动。

## 车辆心跳

车辆以车辆管理中配置的 `Protocol` 选择心跳解析器，并向 RCS 发送：

```http
POST /api/rcs/vehicles/{vehicleId}/heartbeat
Content-Type: application/json
```

报文上限为 64 KB。适配器把车型字段映射成统一遥测模型，至少应尽量上报 `pointCode`（当前地图站点，可带 `_楼层号`）；`z` 表示楼层号，必须为整数，不再另传 `floor`。也可上报 X/Y 坐标、电量和故障。车辆若能报告任务执行状态，还应带上 `taskId`、`commandId`、`routeVersion`、`routeIndex` 和 `routeLength`，这样 RCS 才能将车辆确认的路径进度与预约释放关联。心跳只更新遥测状态，不能代替独立动作命令的执行确认，也不能仅凭心跳中的“收到命令”就确认取货或放货成功。

```json
{
  "pointCode": "0100000376_1",
  "x": 57400,
  "y": 25000,
  "z": 1,
  "status": "Running",
  "taskId": "task-123",
  "commandId": "move-456",
  "routeVersion": 2,
  "routeIndex": 3,
  "routeLength": 12,
  "loadedContainerCode": "TP0001",
  "batteryPercent": 86.5,
  "errorCode": "",
  "errorMessage": ""
}
```

成功时返回 HTTP 200 和更新后的 `VehicleStateDto`；车辆不存在、报文格式不支持或数据越界时返回 HTTP 400；报文超过 64 KB 返回 HTTP 413。RCS 用服务器接收时间记录 `lastHeartbeatAt`，不依赖车辆时钟。要求心跳的协议超过 15 秒没有心跳会标记离线，检查周期为 2 秒；虚拟车协议不要求网络心跳。车辆列表和地图选中车辆侧栏会显示通讯状态、电量、故障和最近心跳。

可在 RCS 主机上用下面的请求验证通用 JSON 解析器（将车辆 ID 和站点替换成实际值）：

```bash
curl -i -X POST "http://127.0.0.1:8224/api/rcs/vehicles/V-01/heartbeat" \
  -H "Content-Type: application/json" \
  -d '{"pointCode":"0100000376","batteryPercent":86.5,"status":"Idle","errorCode":"","errorMessage":""}'
```

现有 `VIRTUAL` 适配器用于模拟运行，不要求心跳；目前尚无真实车型适配器。接入实际车辆时，为该车型实现并注册 `IVehicleProtocolAdapter`，设置 `RequiresHeartbeat = true`，并在 `DecodeHeartbeat` 中把厂商报文解析为 `VehicleHeartbeatTelemetry`。如果不同型号字段、编码或传输方式不同，各自实现解析器即可，统一状态及前端无需跟着厂商报文改变。心跳状态保存在 RCS 运行时缓存，不新增数据库表；车辆上线后第一次有效心跳会建立在线状态，超时会发布离线状态。

适配器负责将统一命令翻译成车型报文、维护车辆通信、把状态和动作结果标准化。`Accepted` 只表示车辆收到命令；适配器必须等到车辆确认独立 fetch/put 命令已执行，才更新 `LoadedContainerCode` 和 `CompletedStepIds` 并发布完成结果。RCS 只在动作步骤确认后更新托盘库存和车辆 UI。算法仍使用 RCS 缓存地图引用，车辆仅接收路径点及坐标，不接收整个地图。

每辆车由 `RcsVehicleRegistry` 按 Protocol 创建独立会话；当前 `VIRTUAL` 会话包含一个独立 `VirtualVehicleSimulator`。各会话隔离位置、载货、活动命令、路径版本、去重缓存和完成步骤。车辆空闲且未载货时可以在管理页面切换协议；切换会重建会话并保留当前地图站点。RCS 调度器按业务规则分配任务；随后 RCS 执行层把全车当前位置和已分配车辆的目标站点同步给 `RCS/Algorithms`。算法不接收任务类型、容器或 fetch/put 动作，只负责多车路线规划及点/线预约。RCS 分别下发纯移动路径和独立站点动作命令。

## 路径命令与站点动作命令分离

路径命令只负责移动，所有路径点的 `Action` 固定为 `move`、`StepId` 为空。车辆到达站点并报告路径完成后，RCS 再单独下发 `EXECUTE_ACTION`。车辆确认动作完成，RCS 才更新库存并规划/发送下一段路径。

```json
{
  "CommandId": "cmd-001",
  "VehicleId": "V-01",
  "TaskId": "123456",
  "Type": "MOVE",
  "RouteVersion": 1,
  "StartPaused": false,
  "Points": [
    { "PointCode": "A", "X": 0, "Y": 0, "Z": 1, "Action": "move", "StepId": "" },
    { "PointCode": "B", "X": 1, "Y": 0, "Z": 1, "Action": "move", "StepId": "" }
  ]
}
```

到达取货点后发送独立动作命令：

```json
{
  "CommandId": "cmd-fetch-001",
  "VehicleId": "V-01",
  "TaskId": "123456",
  "Type": "EXECUTE_ACTION",
  "RouteVersion": 1,
  "Action": "fetch",
  "ActionStepId": "123456:0",
  "ExpectedPointCode": "A",
  "ContainerCode": "TP0000001"
}
```

车辆需分开确认“命令已接收”和“动作已完成”。RCS 核对动作完成结果以及车辆状态中的步骤编号、当前位置和载货编码，再同步库存。取货确认后，RCS 才计算从起点到终点的新路径；到达终点后再发送 `Action=put` 的 `EXECUTE_ACTION`。

| Action | `EXECUTE_ACTION` 车辆行为 |
| --- | --- |
| fetch | 在 ExpectedPointCode 执行取货，设置 LoadedContainerCode；车上已有容器则执行失败。 |
| put | 在 ExpectedPointCode 核对车上容器与 ContainerCode，然后放货并清空 LoadedContainerCode；不一致则执行失败。 |

`ActionStepId` 是业务动作的稳定步骤编号，由 TaskId 和站点数组下标生成。路径点不携带业务步骤；同一位置需要依次执行多个任务动作时，逐条单独下发动作命令。

上游 Auto_Carry 搬运任务的 StationCode 至少两个，默认首站 fetch、末站 put，中间站点 move；手动任务可指定起终点动作；MOVE_ONLY 全部 move。算法只接收目标站点编码，不接收动作信息。

## 分段下发与滚动窗口

路径算法返回完整路线以及按算法设置切分的路径段，RCS 按顺序把路径段交给车辆，不再在执行服务内计算窗口。`MOVE`/`SLIDE_ROUTE` 报文用 `RoutePointOffset` 标记路径段首点在完整路线中的零基位置，`TotalRoutePoints` 标记完整路线长度，`HasMorePoints` 表示后续是否还有算法路径段。例如每段 4 点、经过 1 点续发时，初始段为 1～4；车辆到达第 2 点后，下一段使用 offset 1、ExpectedPointCode=2、points 2～5。实际段大小和续发位置由 RCS 系统设置中的算法设置决定。RCS持续同步全车确认位置及已分配车辆的目标点；算法按当前位置和点/线预约做避让。续发预约冲突时，RCS暂停该车并请求算法基于最新车队状态重规划，得到可预约的新路线后下发新版本并恢复；没有可立即预约的替代路线时恢复原路线并等待资源释放。

地图与路径中点击车辆会显示任务完整路线，以及该车当前和前方仍锁定的路径。完整路线用橙色显示，已确认经过的点及连线会立即释放；当前点和前方锁定的站点、路径线用紫色高亮。算法交通控制器原子预约当前窗口中的点和路径线；车辆确认经过后释放身后的资源，车辆停止或任务结束时保留实际占用点。发生预约冲突时先尝试按当前车队位置和其他车辆的预约重新规划；无法获得替代路线时继续等待资源。车辆状态中的 `LockedPointCodes`、`LockedLineCodes` 用于实时显示当前点及前方剩余预约资源，`LockPointCode` 为活动窗口的末端点。

交通控制器会检测车辆之间的循环等待。检测到循环时，拒绝形成循环的那次续发，执行服务发送 STOP 并保留车辆实际停止位置，避免两车无限互等；该任务会失败，需要操作员检查现场后再重新下发。

续发使用 `SLIDE_ROUTE` 和递增 `RouteVersion`，与暂停后的 `UPDATE_ROUTE` 改路分开。车辆执行窗口时会保留同一个 TaskId 和初始 MOVE 的完成等待；如果下一窗口资源被占用，执行服务先尝试改路，失败后车辆在当前窗口末端等待，直到预约成功后续发，任务取消时仍可通过 STOP 停车。SignalR 路径进度按整条规划路线累计显示。

交通控制器目前随 RCS 单进程运行，预约状态保存在内存中，不是数据库持久锁；部署多个 RCS 实例前必须把算法交通控制服务拆为单一权威实例或改用跨进程共享预约。车辆断连或进程崩溃时不会自动释放真实车辆占用，恢复流程需要先核对车辆现场位置。

虚拟车按原有每点约 300ms 步进运行，不模拟连续运动或制动距离。手动任务选择数据库中的起点托盘后，RCS 等虚拟车确认取货动作，再将托盘和嵌套货物标记为 `IN_TRANSIT`；车上载货编码用于地图车辆标记。车辆确认放货后，RCS 才将托盘及嵌套货物落位到目标站点。未确认的 `Accepted` 不触发库存更新。

## 接收与完成

1. 发送 MOVE/SLIDE_ROUTE，立即收到 `VehicleCommandAck`；Accepted 仅代表路径命令已接受。执行服务等待路径完成结果。
2. 在站点单独发送 `EXECUTE_ACTION`，等待动作命令完成结果并核对车辆状态。
3. 对于 fetch → put 搬运，取货确认后才规划和发送第二段路径；终点路径完成后单独发送 put。只有放货动作确认后，整体任务才完成。
4. 命令结果状态为 COMPLETED、STOPPED 或 FAILED。任务界面持久化显示“叫车任务、取货命令、放货任务、放货命令”四个执行阶段。

相同 CommandId 和相同内容重复发送，返回原确认，不重新执行。相同 CommandId 内容不同会被拒绝。车忙碌时拒绝新 MOVE 覆盖当前任务。最近最多保留 1024 条命令确认/结果，活动 MOVE 在运行期间保留；此缓存为内存数据，超出保留范围或进程重启后不提供永久去重。

## 改路：保留任务，更新剩余路径

使用 `UPDATE_ROUTE`，不取消原任务，也不再创建新的 MOVE。

1. RCS 将当前任务保存为 PAUSED，再发送 PAUSE，并读取车确认的位置和 CompletedStepIds。
2. 用当前地图缓存重新规划尚未完成的业务站点。已经完成的取放货步骤不加入新路径。
3. 发送新 CommandId、原 TaskId、更大的 RouteVersion、ExpectedPointCode 和新 Points。第一点必须是确认的当前位置，Action=move、StepId 为空。
4. 车仅替换剩余路径，保留原 MOVE CommandId、已完成步骤、载货状态和原完成等待。过期版本、位置不一致、换容器或改变已完成步骤会被拒绝。
5. 更新确认时车仍暂停。任务服务保存新路径和地图版本后，原运行任务恢复；原暂停任务保持暂停。

触发入口：`POST {RCS地址}/api/rcs/tasks/{taskId}/replan`，无请求体。成功 HTTP 200 返回任务；任务不适用或重新规划失败返回 HTTP 409 及原因。无法规划时保持暂停，可修复地图后重新规划或取消。此入口更新通往原有未完成站点的路径，不改变任务目标；另有路径预约冲突时的自动绕行尝试。当前 A* 使用实时车位和锁定资源做静态避让，不是时间扩展 MAPF。

## 停止、暂停、继续与重置

命令 Type 支持 MOVE、SLIDE_ROUTE、UPDATE_ROUTE、EXECUTE_ACTION、STOP、PAUSE、RESUME、RESET。`EXECUTE_ACTION` 是独立站点动作命令，必须带 `Action`（fetch/put/move）、`ActionStepId`、当前位置及容器编码；它不携带路径点。控制命令带新 CommandId、VehicleId 和当前 TaskId。RESET 可带 ResetPoint；空值解除定位。

取消活动任务时，执行服务发送 STOP 并确认原 MOVE 的 STOPPED 结果后，任务服务才释放车辆。暂停不执行后续路径点，继续从暂停处运行。STOP 或 RESET 保留车上容器，重置位置不等于放货；恢复带货车辆需要明确安排 put，不能再盲目 fetch。上游 Auto_Carry 使用默认首取末放动作，地图手动任务可分别设置起点和终点的 move/fetch/put 动作。

车辆查询 `/api/rcs/vehicles` 及 SignalR 的 VehicleStateChanged 包含 CommandId、RouteVersion、LoadedContainerCode、LastAction、CompletedStepIds 和 LockPointCode。位置、载货状态及步骤完成信息尚未持久化；服务重启后原执行任务标记 INTERRUPTED，不自动重放取放动作。

命令接收/拒绝、业务站点动作、执行结果和任务控制通过公共日志设施写入 RCS 的 Task 分类。日志不逐次打印完整地图或长路径。

## 验证

适配器切换代码已编译 RCS 后端（0 警告、0 错误）和 Dashboard（0 错误；WCS 任务派发文件有 3 条警告）。未连接运行时数据库或真实车辆。后续增加车型适配器时，应验证接收确认与动作执行确认分离、取放货反馈、断线重连、超时、重复命令、路线窗口冲突、取消和车辆重启恢复。

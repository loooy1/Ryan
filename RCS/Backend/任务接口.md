# RCS 任务接口

更新日期：2026-10-06。

## 1. 接收任务

`POST {RCS后端地址}/api/v1/task_receive`

仓库默认 RCS 地址为 `http://localhost:8232`，实际监听以 RCS 后端配置为准。请求使用 HTTP JSON，`Content-Type: application/json`，UTF-8。

```json
{
  "GroupId": "order001",
  "MsgTime": "2025-04-25 17:00:00",
  "PriorityCode": 1,
  "Warehouse": "Show",
  "Tasks": [
    {
      "TaskId": "123456",
      "TaskType": "Auto_Carry",
      "ContainerCode": "TP0000001",
      "StationCode": ["1800_1", "2600_1"],
      "AreaCode": []
    }
  ]
}
```

示例中的场景和站点必须替换为当前 RCS 地图中的实际值。地图点的 Z 字段代表整数楼层号；自动任务的 StationCode 必须将点编码与 Z 拼为 `站点号_楼层号`。

AUTO/MANUAL 是每台车辆自己的运行模式，不是 RCS 全局开关。上游调用此接口后，合法任务会写入 `rcs_tasks`，并标记为 UPSTREAM 来源；没有可用自动车辆时任务保持 WAITING，不会因缺少车辆而拒绝或丢弃。调度器只将上游任务分配给已启用、空闲且处于 AUTO 的车辆。车辆模式在“车辆管理”中配置并保存在 `rcs_vehicles.operating_mode`，新车默认 AUTO。

RCS 界面手动任务只在“地图与路径”中选中 MANUAL 车辆后下发。任务窗口场景默认当前地图场景；起点和终点分别选择站点及动作（move、fetch、put），任一站点选择 fetch/put 时还要填写容器编码。任务写入数据库后会直接绑定该车并启动执行，不经过调度器；车辆忙碌时返回 HTTP 409，不排队。“任务”页面只查看上游原始任务和上游任务拆分记录，不提供手动任务创建，也不显示 MANUAL 来源记录。自动和手动任务共用任务表、路径算法和车辆协议。切换车辆模式不会中止已开始的任务；上游等待任务等 AUTO 车辆空闲后由调度器处理。

| 字段 | 规则 |
| --- | --- |
| GroupId | 必填，最多 128 字符；用于关联同组任务。组内每条任务独立排队，不锁定整个组连续执行。 |
| MsgTime | 本地时间字符串，严格使用 `yyyy-MM-dd HH:mm:ss`，精确到秒。目前校验格式，不按报文时间判断新旧。 |
| PriorityCode | 非负整数，越小越优先；同优先级按入队顺序执行。同报文按 Tasks 数组顺序接收。 |
| Warehouse | 必填，必须与当前地图 SceneName 一致。 |
| Tasks | 1～100 项；一个报文内 TaskId 不可重复。 |
| TaskId | 必填，最多 128 字符，任务唯一标识。 |
| TaskType | 上游仅支持 MOVE_ONLY、Auto_Carry。Auto_Carry 为搬运任务，默认首站取货、末站放货，中间站点仅移动。手动接口另支持 MANUAL，由 StationActions 指定各站动作。 |
| ContainerCode | 字符串，最多 128 字符；MOVE_ONLY 可为空，Auto_Carry 必填。 |
| StationCode | 自动任务必须传 `站点号_楼层号`，如 `0100000347_1`；楼层号必须与地图站点的 Z 值一致。Auto_Carry 至少两个站点。RCS 校验后解析为地图内部站点编码，并按数组顺序访问。 |
| StationActions | 可选；非空时数量必须与 StationCode 相同，逐项对应 move、fetch、put。任何点选择 fetch/put 都必须填写 ContainerCode。省略时按 TaskType 使用默认动作。 |
| AreaCode | 数组，允许为空，最多 100 项；目前保存，不据此自动选择站点。 |
| VehicleId | 上游可选，空字符串时自动分配；指定时任务只分给该车辆，车辆停用或处于 MANUAL 时留在 WAITING，车辆重新启用并设为 AUTO 后可继续调度。编号最多 64 字符；不存在返回 400。RCS 手动界面创建的任务必须指定已启用的 MANUAL 车辆。 |

已有车辆位置时，先规划当前位置到第一个站点，再按顺序访问后续站点。车辆尚未定位时，将第一个站点作为初始位置。规划读取 RCS 地图缓存，不逐次查询地图数据库；同次执行使用同一份缓存快照。

## 2. 接收结果与重复请求

自动任务接口和 RCS 界面手动任务接口统一使用简洁确认响应，仅包含 `msgTime`、`success`、`exception`。成功时 `success` 为布尔值 `true`、`exception` 为 `null`；失败时 `success` 为 `false`、`exception` 为错误原因。HTTP 状态码仍用于区分成功、请求错误和任务冲突。

成功示例（HTTP 200）：

```json
{
  "msgTime": "2026-10-06 17:00:00",
  "success": true,
  "exception": null
}
```

失败示例（例如 TaskId 重复，HTTP 409）：

```json
{
  "msgTime": "2026-10-06 17:00:00",
  "success": false,
  "exception": "任务id重复"
}
```

**接收成功表示任务已持久化并进入队列，不代表车辆执行完成。** 状态、车辆、路径、时间和失败原因通过任务查询接口读取。

- 参数格式、场景或站点不合法：HTTP 400，返回可读原因，整批新任务不接收。
- TaskId 已存在且业务内容一致：返回原任务，不重复创建或执行。重复请求允许更新 MsgTime，不影响原任务记录。
- TaskId 已存在但业务内容不同：HTTP 409，整批新任务不接收。
- 没有通路：接收后正式规划时将任务标记为 FAILED，保存原因，不阻塞后面的任务。

默认响应字段采用 camelCase；请求兼容示例中的 PascalCase。

## 3. 调度与控制

支持多台虚拟车并行执行，每车一次执行一个任务。默认按车辆编号挑选启用且空闲的车辆，任务按 PriorityCode 和入队顺序分配。指定车辆忙碌时该任务等待，其他空闲车辆可执行符合条件的后续任务。高优先级不抢占已有任务。同一辆车的上一个任务终态保存后，才分配下一个任务。

| 方法与路径 | 用途与结果 |
| --- | --- |
| GET /api/rcs/tasks?limit=100 | 最近任务列表，按入队 Id 倒序；limit 限制为 1～500。 |
| GET /api/rcs/tasks/{taskId} | 单任务详情；不存在返回 404。 |
| POST /api/rcs/tasks/manual | 地图与路径页面创建移动或搬运任务，必须指定空闲的 MANUAL 车辆；直接启动，不进调度队列，车辆忙碌返回 409。正文结构与上游任务组相同。 |
| POST /api/rcs/tasks/{taskId}/pause | 暂停当前执行任务，成功 204，不符合状态返回 409。 |
| POST /api/rcs/tasks/{taskId}/resume | 继续暂停的任务，成功 204，不符合状态返回 409。 |
| POST /api/rcs/tasks/{taskId}/replan | 使用当前缓存地图从确认位置更新剩余路径；成功 200，冲突 409。运行任务更新后恢复，暂停任务保持暂停，规划失败保持暂停。 |
| POST /api/rcs/tasks/{taskId}/cancel | 取消等待或执行中的任务，成功 204，不存在或已经结束返回 409。执行中取消的终态稍后变为 CANCELLED。 |

任务状态：

| 状态 | 含义 |
| --- | --- |
| WAITING | 等待分配。 |
| RUNNING | 已分配，正在规划或执行。 |
| PAUSED | 已暂停；该车辆仍被占用，其他车辆继续执行。 |
| CANCELLING | 已接受取消，正在停止车辆执行。 |
| COMPLETED | 虚拟车到达最终站点，并完成该点动作。 |
| FAILED | 地图、路径或执行异常；message 给出原因。 |
| CANCELLED | 任务已取消。 |
| INTERRUPTED | 服务停止或重启造成执行中断。 |

“车辆管理”页面只配置车辆名称、启用状态和当前位置，并提供增删；运行模式仍在地图选中车辆后切换。创建时可指定初始当前位置。“任务”页面只显示上游任务，不创建或显示手动任务。手动任务操作位于“地图与路径”：选中 MANUAL 车辆后，右侧提供暂停、继续、停止及下发任务按钮。地图任务窗口显示当前场景，起点默认使用车辆当前位置，起终点可手动输入或点选地图站点填入，并分别选择 move/fetch/put 动作；包含取放动作时需填写容器编码。通过 `/api/rcs/tasks/manual` 直接绑定选中的 MANUAL 车辆并启动，不进调度队列。点选起终点时保持车辆选中，车与站点重合时直接填入站点。普通选择模式下，车辆与站点或其他车辆重合时弹出菜单分别选择，选中车辆以黄色外框标识。地图不显示路径选择或车辆概览。更改车辆当前位置通过车辆重置接口保存；正在运行或暂停时禁止修改。

## 车辆管理接口

| 方法与路径 | 用途 |
| --- | --- |
| GET /api/rcs/vehicles、/api/rcs/vehicles/{id} | 车辆列表或单车状态。 |
| POST /api/rcs/vehicles | 创建车辆，正文含 Id、Name、PointCode、IsEnabled、OperatingMode（AUTO/MANUAL）；成功 201。 |
| PUT /api/rcs/vehicles/{id} | 修改 Name、IsEnabled、OperatingMode；成功 200。停用或切换模式只影响后续分配，当前任务继续执行。 |
| DELETE /api/rcs/vehicles/{id} | 删除空闲车辆，成功 204；存在活动任务、载货或指定等待任务时返回 409。 |
| POST /api/rcs/vehicles/{id}/run | 正文含 StartPointCode、EndPointCode，创建指定车辆移动任务。 |
| POST /api/rcs/vehicles/{id}/pause、resume、stop | 控制该车活动任务；成功 204，不适用 409。 |
| POST /api/rcs/vehicles/{id}/reset | 正文为站点编码字符串（如 "P1"），空字符串解除定位；成功 204，并保存初始位置配置。 |
| PUT /api/rcs/vehicles/{id}/position | 正文为站点编码字符串；空字符串解除定位。保存当前位置，车辆有活动任务时返回 409，不会取消任务。 |

## 4. 存储、重启与实时消息

- 私有实体和存储位于 RCS 后端，公开报文位于 `Shared/Contracts/Rcs/Tasks`。
- 迁移 `AddRcsTaskLayer` 创建 `rcs_tasks`。任务表包含 TaskId 唯一索引及排队索引，没有外键。
- 后端启动沿用 `InitializeSharedDatabaseAsync` 自动应用迁移，再恢复任务状态。
- 重启后 WAITING 任务继续排队；原 RUNNING、PAUSED、CANCELLING 任务标记 INTERRUPTED，不自动重放。需确认车辆位置后，使用新 TaskId 重新下发。
- `AddRcsVehicles` 创建 `rcs_vehicles` 并为首次迁移初始化 V-01，同时给任务增加 requested_vehicle_id。车辆编号、名称、启用状态、初始站点持久化；没有外键，车辆表仅编号主键，没有额外索引。
- 每步运行位置、载货和已完成步骤仍为内存状态；重启恢复设置过的初始站点，不恢复中断时的实时位置或自动重放动作。
- SignalR 增加 `VehiclesChanged` 全列表通知，用于车辆增删和配置变化；`VehicleStateChanged` 按车辆推送运行状态。前端重连后 HTTP 重读列表。
- `/hubs/rcs-realtime` 发布 `TaskChanged`，车辆状态包括 TaskId、CommandId、RouteVersion、LoadedContainerCode、LastAction 和 CompletedStepIds。首次连接和重连后应通过 HTTP 查询当前任务状态。
- 接收、分配、路径生成、暂停、继续、取消、完成和失败使用公共日志设施，分类为 Task。

当前以单个 RCS 后端实例为运行前提，不支持多个实例共同调度同一辆车。

## 5. 应用层职责

应用层已分为 `Application/Tasks`、`Application/Scheduling`、`Application/Execution`：

- `RcsTaskService` 负责接收、幂等、保存和任务状态，通过接口协调调度与执行。
- `IRcsTaskScheduler.Select` 输入等待任务摘要和车辆状态，返回任务与车辆的分配结果；当前实现 `RcsTaskScheduler` 使用优先级/FIFO，只分配空闲或已到达车辆，不访问数据库、算法或车辆对象。
- `IRcsTaskExecutionService` 负责地图检查、向算法同步车队位置和目标站点、把路线转成车辆协议并执行；实现不更新任务表，也不选择下一任务。
- `RCS/Algorithms` 的多车交通控制器维护全车位置、各车目标站点和点/线预约。路径规划接口不接收业务任务类型、容器或点位动作；RCS 在下发车辆协议前再附加动作。当前 A* 优先避开其他车辆的当前位置与已预约资源，续发冲突时尝试自动改路。
- `RcsTaskDispatchWorker` 驱动后台循环，规划与执行结束后由任务服务保存终态，再分配下一任务。

调度策略在 `RcsModuleExtensions` 通过接口注册，可以替换实现。调度仍由 RCS 执行；算法交通控制器当前以 `RCS/Algorithms` 类库形式同进程运行，后续可通过独立传输适配器拆成服务。当前实现有实时位置感知、资源锁与冲突改路，不是时间扩展 MAPF。文件和调用关系见 [应用层说明](Modules/Rcs/Application/README.md)。

## 6. 当前验证范围

RCS 后端和 Dashboard 使用隔离配置 TaskVerification 编译。临时内存存储配合真实 HTTP 控制器、任务服务、算法和虚拟车验证优先级/FIFO、串行执行、12 次并发重复提交、冲突、非法批次、暂停继续、取消重置、移动操作入队和中断恢复。

拆分后的检查还覆盖空任务、无车辆、暂停车辆不可分配、长队列优先级、规划后刷新地图仍使用原快照、规划期间暂停后规划失败不阻塞下一任务，以及替换 IRcsTaskScheduler 后实际分配顺序随之改变。

多车检查覆盖并行执行、每车占用、指定车辆等待与后续任务分配、单车暂停/继续/停止/重置/改路、停用和重新启用、车辆增删限制，以及从内存存储重新初始化车辆配置。后台服务停止时，验证运行和暂停车辆全部停止、任务标记 INTERRUPTED、载货保留且禁止删除带货车辆。前端界面检查覆盖添加车辆、保存配置、指定车辆移动、实时状态变化及非法编号错误反馈。

当前前端界面检查使用临时内存服务，覆盖车辆管理仅参数配置、地图弹窗起终点输入与点选、车点重合时站点填入不切换车辆、无效站点和无通路错误保留输入、成功提交关闭窗口、地图暂停和停止操作、取消后控制恢复。未连接实际数据库。

按用户要求未验证 MySQL 建表及数据读写。正常运行的后端仍需重新编译、重启才能加载本次代码和迁移。

取放货现已通过路径点动作模拟，不更新库存。执行服务通过 IVehicleCommandChannel 下发车辆报文，取消会发送 STOP，改路使用 UPDATE_ROUTE 保留任务和已完成动作。当前交通控制器在 RCS 进程内存中独占预约路径窗口中的站点和连线；遇到冲突会先尝试避让改路，暂时无替代路线时等待资源。尚不包含区域选点、真实车辆网络通信、跨 RCS 进程的共享锁、时间扩展 MAPF、WCS 完成回调或完整 GRCS 协议兼容。协议和改路规则见 [车辆协议](车辆协议.md)。
